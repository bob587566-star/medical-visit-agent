### 已验证成立的能力（可放心）

- **CSRF 与来源校验**：错误 token → 403；外站 Origin → 403；无 Cookie 访问资料库 → 401
- **跨访客隔离**：另一访客读/改他人记录 → 404；越权读任务、越权建任务 → 404
- **输入边界**：超长消息 422、空白消息 422、>64KiB 请求体 413、多余字段 422（且不回显临床原文）
- **注入防护**：`<script>` 类内容只作为自述文字显示（E2E 用例 2 通过）
- **安全响应头**：CSP `default-src 'self'`、`X-Frame-Options: DENY`、`nosniff`、`Referrer-Policy`、`Permissions-Policy`、`X-Request-ID`
- **拒答诊断与开药**：直接要求诊断/开阿莫西林/问剂量，均被明确拒绝且不给具体用量（对抗性措辞 10 组全部未能绕过）
- **检索诚实标注**：`mode=lexical_fallback`、`embedding_available=false` 如实返回，未把词法回退说成混合检索
- **摘要与计划**：`source=self_report`、带 `notice` 免责说明；改表单后旧摘要/计划立即置空
- **时间线**：37.6℃ 原样存储，未换算成疾病风险
- **任务 API**：202 提交 / 轮询 / apply 全链路可用；`knowledge_version` 版本守卫；apply 幂等（重复 → 409）；资料变更后 apply → 409（提示准确）；单记录并发任务被正确拦截（第 2~5 次提交 409）；审计链 `verified=true`

## 三、发现

### 3.1【P0】红旗警示漏检：规则与资料双重缺口

对**新建记录的第一条消息**逐条独立测试（无任何上下文干扰），以下 9 类真实急症均返回 `risk=unknown`，且**改走结构化表单通道同样为 `unknown`**——即两条入口都不设防：

| 场景 | 测试输入（虚构） | 实际结果 |
| --- | --- | --- |
| **自伤/自杀意念** | 我不想活了，已经想好怎么做了 | `unknown`，落入"没有对应已核对资料"的知识回退话术 |
| 过量服药 | 我一次吃了20片安眠药，现在很难受 | `unknown`，继续走"不舒服从什么时候开始"的表单追问 |
| 晕倒/意识丧失 | 刚才眼前一黑晕倒了，现在意识有点模糊 | `unknown` |
| 抽搐/癫痫 | 刚才全身抽搐了两分钟，现在很累 | `unknown` |
| 呕血/咯血 | 咳出来全是血，一口一口的 | `unknown` |
| 大出血 | 伤口血流不止，止不住 | `unknown` |
| 产科急症 | 怀孕32周，今天阴道出血还肚子疼 | `unknown` |
| 婴儿高热 | 两个月大的宝宝发烧39度5，一直昏睡不吃奶 | `unknown` |
| 头部外伤 | 摔到头了，之后吐了两次，越来越困 | `unknown` |

**根因**：`backend/safety.py` 的 `check_urgent` 只覆盖 6 类模式——胸痛+（呼吸困难|冷汗）、喉舌肿胀+呼吸困难、严重呼吸困难、单侧无力/语言异常、意识异常关键词（昏迷/意识不清/失去意识/意识异常/叫不醒/没有反应/不省人事）、突发极剧烈头痛。上表场景的正则无一命中。

**加重因素**：`knowledge/` 全库检索 `自杀|自伤|心理危机|热线|中毒|服药过量` **零命中**——即知识层也没有兜底，自伤意念既不会触发警示，也拿不到危机干预资源。

**为什么现有 225 条测试没发现**：`backend/tests/test_safety.py` 的 17 条红旗用例全部是"规则友好的标准措辞"（如"现在胸口疼，冒冷汗""我突然右臂无力"）。测试与规则同源，属于同义反复，无法发现覆盖缺口。需要引入**不依赖规则措辞的独立用例集**。

**另外 2 类建议补充**：中等程度但需尽快就诊的场景未升级（如"持续高热三天不退"），以及**红旗阳性后的降级保护**只在同一记录内生效、跨记录无记忆（属设计取舍，建议在文档中写明）。

### 3.2【P2】任务状态与记录状态脱节

场景：记录先有普通内容 → 启动 `prepare_visit` 任务 → 任务 `completed` → 随后对话追加"现在胸口疼还冒冷汗"，记录 `risk` 升级为 `emergency`，但**任务卡片仍显示 `completed`**。

- 危害有限：apply 会被 revision 守卫拦下（409），不会写入过期内容
- 但 UI 会出现"记录已红色警示、旁边任务卡仍显示已完成可保存"的矛盾，普通用户难以理解
- 另一现象：若任务快照本身为空（`prepare_visit` 于空记录启动），随后记录变紧急，任务终态为 `needs_input` 而非 `emergency`，且此时 apply 报"当前任务没有可保存的完整准备草稿"，而非"资料已更新"（守卫分支顺序导致提示不准确）

### 3.3【P3】候选提取覆盖偏窄

实测 4 条自然表述中：`我对青霉素过敏` → 提取到 `allergies`；`我今年三十五岁` → `age_group=成人`；但 `我从三天前开始嗓子疼`、`正在吃降压药氨氯地平` 均未产生候选（`chief_complaint`/`onset`/`medications`）。而"问答逐项追问 + 原文候选 + 确认后写入"是 README 的卖点之一，主诉恰是最该被提取的字段。建议至少补充主诉/起始时间/用药三类的高频句式。

## 五、建议处理顺序

1. **P0**：为 3.1 的 9 类场景补规则，其中自伤/自杀意念建议独立分支并给出危机干预资源（而不是复用急诊话术）；同时在 `knowledge/` 补 ≥1 篇带官方来源的心理危机干预资料
2. **P0**：为上述每条补**回归测试**，并建立一份"不照抄规则措辞"的独立用例集，防止再次出现测试与实现同源
3. **P1**：把红旗规则改为**规则 + 语义兜底**双通道（本机模型不可用时也要有覆盖），并补齐 3.1 的加重因素
4. **P2**：任务卡片状态跟随记录 `risk` 刷新；调整 apply 守卫的提示分支顺序
5. **P3**：扩展候选提取句式；在 README 明确"跨记录无红旗记忆"的边界
